# graph 之後不是更多拓撲，是不變量加存證——而那一層正在被平台先佔

> 2026-09-12 查證 + 討論。draft，定位型。
> 怎麼冒出來的：問「graph engineering 之後會是什麼」。是 [graph engineering 定位](2026-09-12-graph-engineering定位與六條接口.md) 的下一格，但結論對 knowie 一半是好消息一半是壞消息。

## 現況：還沒被命名，東西已經在出貨
prompt → context → harness → loop → graph 這條線，**下一格沒有定名**。兩輪搜尋一致：有人喊 Agent OS、有人喊 fleet，都還在試詞。現在誰講得出那個名字，多半在賣東西。

但產品已經在架上，而且**不是另一層拓撲**：
- **控制面**：Microsoft 的 agent fleet 控制面 2026-05-01 GA，每人每月 15 美元，管理員拿到列出組織內每個 agent 的**中央註冊表**。Google Cloud Next 2026 推 **Agent Identity + Agent Registry**，明講要取代各家自拼的治理土炮。
- **治理單位換成艦隊**：目前多數治理討論被評為「搞錯單位」——企業現實是一群 agent 散在各部門，各碰不同資料、各帶不同風險。學術端也有對應物（Parsons 制度架構 × 網際網路規模 agent 社會）。

## 判斷：槓桿從結構移到「不變量 + 證據」
每一層都是在**前一層的失敗模式變成日常**時才被命名。loop 的失敗是一個迴圈做不了多專業的活 → graph。

graph 自己列的失敗裡，有一條**不可能在 graph 層內解決**：**unvalidated graph generation**，也就是 agent 開始自己生成拓撲。一旦拓撲是 agent 寫的，人的槓桿就不在「設計那張圖」，而在兩件事：**無論跑成什麼樣都必須保持為真的是什麼**，以及**怎麼證明它真的被遵守**。

所以預測的產出物是：一份系統不准自己改寫的約束、一份誰有否決權的規定、一條可驗證的證據鏈（某決定是誰在何時做的、哪條約束被檢查過）。**治理加存證，不是更多結構。**

## 對 knowie：好消息不重要，壞消息重要
好消息是那正是 knowie 的論點：根本原則 + 人定案主權 + git 留痕，剛好三件。

**但這個結論太順著我們自己的說法了，所以要先把反面講足**（[mattpocock 鄰居](2026-08-26-mattpocock-skills-doing-lane鄰居.md) 那條「別自我安慰」的同一紀律）。

### 情境一：平台捕獲（主要威脅）
這一層正在被當成**付費平台的控制面**蓋，附身分與註冊表——正是 knowie 明確拒絕站的位置。[競品與生存空間](2026-06-06-競品與生存空間.md) 記的威脅是「某個工具自己長出持久 why 記憶、把這層吸收掉」；**艦隊控制面是那個威脅的放大版**，而對手是 Microsoft 與 Google，不是一個 npm 套件。

### 情境二：鷹架通縮
這整疊有一半在補模型的不足。長時程可靠性上來後，harness/loop/graph 會**壓縮成函式庫而非學科**（對照：context window 變長後 prompt engineering 塌掉一半）。knowie 在此情境相對耐命——它記的不是模型的弱點，是**人做過的決定**——但「loop 需要 grounding」這條對外說法會跟著失效，得換一套說法。

### 情境三：跨組織 agent 社會（最遠，也最有利）
治理問題變成跨方的契約與信譽，那是**協議形狀**的問題，不是平台形狀的。這一格對「跨廠商、純 markdown、活在使用者自己 git 裡」的 why 層才有**結構性優勢**（[協議非平台](../concepts/協議非平台.md)）。

## 現在該準備的只有一件：存證
knowie 已有 why 與 git，缺的是讓「**這個決定是人做的、在這裡、當時、而且這條約束被檢查過**」成為機器可驗的東西。那正好是 [graph 六條接口](2026-09-12-graph-engineering定位與六條接口.md) 的第 4、5 條（錨點硬化成閘門、judge 當 checker node 並引用理由）。**兩份 draft 指向同一個動作，這是它值得先做的證據。**

**不要蓋註冊表，不要蓋控制面。** 那是平台的活，打不過也不該打。

## 待想
- 情境二若成真，對外說法換成什麼？候選：「why 不是鷹架，鷹架會被模型吸收，決定不會」——待打磨。
- 存證要到什麼強度？git commit 的 author + 簽章夠不夠，還是要獨立的 attestation 格式？過度工程的風險很高。
- 平台捕獲若發生，knowie 的出路是被掛載（adapter 餵進它們的控制面）還是保持獨立？對上 [FUSE 掛載](2026-06-07-檢索機制-graph還是path.md) 那條北極星。
- 這份的預測**沒有兌現機制**。該設一個回頭檢查的觸發條件，否則它會變成一份沒人回來對帳的預言。
