# 知識條目的形狀——命名、段落、強調，決定它能不能被召回和剪枝

> 2026-08-14 五專案外推審計。draft，design 型。
> 怎麼冒出來的：看五個真實專案（ArduinoCAD / VizGPT / KnowField / semorphe / wewayfinders）的 `knowledge/` 品質。機械層大多健康，差異全在**條目長什麼樣**——而三個專案各自演化出了不同的形狀，方向一致。
>
> **已提升（2026-08-14）**：→ [vision 路線圖「知識條目的形狀（模板 + `_core`）」](../vision.md)。觀察四已回流 [experience](../experience.md)「skill 該寫成判準」的擴張。本檔為在建設計脈絡，留到該項完成才兌現出列。

## 觀察一：concept 的名字該是斷言，不是名詞

兩種命名風格，效果差很多：

| 專案 | concept 命名 | 形態 |
|---|---|---|
| wewayfinders | `複述一份真相就是排定它過期的日子`、`看過不算被看見才算`、`被記錄不等於被同意`、`訊號與它的意義會分開` | **斷言句** |
| VizGPT | `一張圖分不出來的兩件事`、`規矩住在哪裡`、`一位學生能不能自己說出來` | 斷言／提問 |
| semorphe | `投影`、`元件`、`性狀`、`執行機構` | 名詞 |

名詞只能拿來**歸檔**（這段文字屬於哪一類）；斷言句可以拿來**判**（這段文字該不該進來）。

[`_core`](../../skills/_core.md) 的測試問「Real parent-concept or fake? → Does it have pruning power?」——**斷言式命名讓這個測試在命名當下就通過**，名詞式要等到概念抓不住東西了才發現。這正是 [收斂](../concepts/收斂.md) 的「母概念要有剪枝力」在命名層的具體化，也是 [蒸餾](../concepts/蒸餾.md)「名字是認出的」的下一步——認出來之後，**認成什麼詞性**還有選擇。

> 反例確認：semorphe 是五個裡 concept 最多的（12 個），但它的 concept 更像領域詞彙表而非判準集。concept 多不等於收斂器官強。

**提案**：`_core` 的 tests 補一句——a concept's name should be a **claim you can judge text against**, not a noun you can file text under。同步進 `concepts-README` 模板（en + zh-TW）。

## 觀察二：四段式該升版——三個專案獨立指向同一個缺口

實測 experience 的段落標籤分布：

| 專案 | 用的段落 |
|---|---|
| wewayfinders | 理論說／實際發生／解決方式／教訓（73/73 完整） |
| VizGPT | 原版 ＋ **自己在檔頭明文定義的「做法」例外**（213/285 用理論說） |
| semorphe | **怎麼撞到的／怎麼用／不適用的時候／判準／相關** |

一開始我以為 semorphe 是不合規，打開才知道是**演化**，而且比原版好在兩個明確的地方：

- **「不適用的時候」**——原版四段式**完全沒有邊界條件**。一條沒有邊界的教訓會被過度套用；VizGPT 285 條裡有大量其實是同一條在不同情境下重寫的，缺的正是這一段。這是 pruning power 在教訓層的對應物，目前只存在於 skill 層（`_core` 的 tests 有、模板沒有）。
- **「相關」出現 63 次**——他自己建了 lesson ↔ lesson 的**橫向**連結。knowie 的模型只有 `experience → concepts` 的縱向收斂，沒有橫向；semorphe 是在補這個洞。

VizGPT 也在檔頭給自己開了例外並寫了理由，值得整段引用：

> **例外：程序型教訓用「做法」取代「理論說」。**
> 四段式的第一段是要記下「原本以為的樣子」——而有些教訓沒有那個落差，
> 它們是「我這樣做了，而它救了我」。硬套「理論說」會逼出一個編造的錯誤預期，
> 而那比形式不一致更糟。

**三條獨立推導指向同一件事**（semorphe 換 schema、VizGPT 開例外、wewayfinders 保持原版但掉來源）。照 [收斂](../concepts/收斂.md) 的「多條獨立推導＝真根」，這夠格動模板。

**提案**：`experience.md.tmpl` 升為——
- 必要：**實際發生 / 教訓 / 來源**（三段不得省）
- 首段二選一：**理論說**（有落差時）或 **怎麼撞到的**（程序型，無落差時）
- 可選但鼓勵：**不適用的時候**（邊界）、**相關**（橫向連結）

## 觀察三：來源是最容易掉的那條腿

| 專案 | 教訓數 | 有「來源」 |
|---|---|---|
| ArduinoCAD | 34 | 34 ✅ |
| KnowField | 34 | 34 ✅ |
| VizGPT | 285 | 285 ✅ |
| semorphe | 109 | **46** |
| wewayfinders | 73 | **19** |

semorphe 63 條、wewayfinders 54 條教訓**沒有來源**。這直接違反 [根本原則二](../principles.md)（記憶可大致回溯）：教訓還在，但「它從哪一次撞出來的」沒了，半年後重建不回當時的認知——留下的是結論，丟掉的是[可回憶單元](../concepts/記憶系統.md)的 how 腿。

值得注意的是**分岔的代價**：schema 演化得最兇的兩個專案，掉的都是來源。改形狀的時候，最先被省略的是那段「看起來只是記帳」的。

而**這是 grep 得到的** → 見 [judge再機械一階](2026-08-14-judge再機械一階.md)。

## 觀察四：教訓寫成「判準」才跨處境，寫成「做法」會隨技術棧過期

對照教訓的標題句式：

- **做法式**（ArduinoCAD 居多）：「UI 難 TDD？把綁定層與算繪分離就能測」「接兩座標系：抽一個縮放常數當單一橋」
- **判準式**（wewayfinders / VizGPT / semorphe 居多）：「否決被推翻時，要問它擔心的事是否以另一種形式成真」「一個會改變被測對象的量測器，量到的不是被測對象」「量測的解析度小於要量的效果時，換一個量測對象」

做法會隨技術棧過期（換掉 Blockly、換掉 Three.js，那條就死了）；判準跨處境。

**而 knowie 已經有這條判準了，只是沒套到 experience 上**——[experience](../experience.md)「skill 該寫成判準，不是窮舉流程」：

> 完整性來自**生成式**（判準 + 不變量 + 根公理，讓 AI 推導），不是**窮舉**。

那條當初是為 skill 寫的。**同一條判準對 experience 同樣成立，而沒有人把它搬過去**——這是一個判準被寫下、卻沒被套到相鄰器官上的例子。（形狀同 [experience](../experience.md)「反覆使用的隱性判準，會以為已固化」。）

semorphe 有一條示範了判準式的極限形態：

> 「決定投入打磨之前，先問這個領域有沒有證據說打磨會兌現」
> ——查完六十年文獻後，他**改掉的不是結論，是驗收的寫法**：從「訊息變好了」
> 改成「兩個數字都要記，而假警報只准下降」，一個**就算打磨無效也量得出來**的判準。

→ 可提煉成一條驗收標準：**一條教訓完成的標誌，是它改掉了某個判準的寫法，而不是它被記下來了。**

## 觀察五：強調是預算，而五個專案全部透支

**行內**強調密度（不含 `- **理論說**：` 這類結構標籤——見下方更正）與 ⚠️ 總數：

| 專案 | 行內強調/行（experience） | ⚠️（全庫） |
|---|---|---|
| ArduinoCAD | **0.77** | 8 |
| knowie 自己 | 0.61 | 25 |
| VizGPT | 0.57 | 7 |
| wewayfinders | 0.45 | **894** |
| semorphe | 0.42 | **807** |
| KnowField | 0.42 | 1 |

> **更正（2026-08-14，套用到自己時發現）**：初版用的是「所有 `**…**` / 行」，把每條教訓固定的五個段落標籤算成了強調——**等於在懲罰格式合規**（教訓愈密的檔標籤愈多）。照那個數字 knowie 自己是 1.29「全集最差」，分開之後是 0.61 的中段，最差的是 ArduinoCAD。
>
> 更重要的是：修正後六個庫落在 **0.42–0.77**，不到 2 倍全距，而我主觀認為寫得最好的那份庫（wewayfinders）在 0.45、第二好的 semorphe 在 0.42——**這個指標分不開好壞到足以當紅旗**。所以它留在 `_core` 當**寫作判準**，不進 judge 當掃描。這是本批第二條因為跑真實資料而降級的（第一條是 history 檔名詞彙），同一個教訓：**「可機械化」要拿真實分佈驗，不是想當然。**

五個庫裡寫得最好的那份 concept（wewayfinders 的 `複述一份真相…`）一頁裡有 20 幾個 ⚠️、上百處粗體。**當每句都是重點，就沒有重點**——真正的判準句反而沉下去。

這對 AI 讀者的代價比對人更大：粗體和 ⚠️ 就是給 attention 的訊號，訊噪比降低會**直接降低召回精度**——而召回率正是 [experience](../experience.md)「why 對齊的引擎是 next 的預防」裡已驗證的那個價值引擎。所以這不是美學問題，是在價值鏈上。

**提案**：`_core` 目前只管措辭（necessary friction vs theater），沒管排版。補一句——emphasis is a budget：**⚠️ 保留給「這裡我曾經錯過」，粗體保留給「這句本身是判準」**。一份文件超過 ~5 個 ⚠️ 等於 0 個。

（本檔自己遵守：全篇 0 個 ⚠️。）
