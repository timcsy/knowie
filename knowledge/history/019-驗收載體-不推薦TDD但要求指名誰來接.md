# 019：驗收載體 — knowie 不推薦 TDD，但要求指名誰來接

> 2026-09-12。一條定位決策。起點是問「沒裝 SDD 工具的專案，knowie 會不會鼓勵 TDD 和 git」。

## 轉移
- **舊（superseded）**：`next` 的 step 5 寫「把 brief 的 cautions 交給 spec 工具」。沒有 spec 工具的專案裡，這句話**沒有收件人**——brief 在對話裡被讀一次，實作時蒸發，acceptance 那行沒有任何東西接住。git 同時是整套機制的地基，卻從未對使用者講明，CLI 也不檢查。
- **新（current）**：三件事分開放，不混成一句「建議你用 TDD」。
  - `next` step 5 **分支**：`.knowie.json` → `tools` 有 spec 工具就交給它；沒有就**指名載體**——可執行測試最強（唯一會在幾個月後自己叫的），PR checklist／commit trailer 次之。判準：這條 acceptance 是不是只有人記得才會 fail？是的話它沒有載體。
  - `init` 的引導對話多問一句「這個專案怎麼判定一個改動完成」。答案寫進**使用者自己的** `principles.md`，之後 `next`／`judge` 拿它對 code。「還沒有做法」是真答案，寧可不記也不裝一個他沒選的習慣。
  - CLI `init` 檢查是不是 git repo，缺了就說明為什麼需要——**一次，不是每輪**。

## 為什麼這樣切
1. **TDD 是 what-lane 的實踐**，knowie 推它就牴觸根公理二與延伸原則 7。但 `next` 本來就要求 acceptance 可驗證——所以「用測試接住」是**從 knowie 自己的判準推出的結論**，不是進口的意見。差別很實在：推導出來的在 notebook／探索型專案會自然讓步成別的載體；進口的會被整批忽略，然後連帶蝕掉 skill 其他部分的權威。
2. **git 不是偏好，是 knowie 自己的地基**：延伸原則 4 的「自動整理敢自動，因為可審可回滾」、`draft` 衰減讀 git 新近度、`migrate` 從 log 重建 why。講它是在說明自己的運作前提，不是管人家怎麼寫 code。
3. **位置決定存活。** 一次性前提放 `init`；每輪都響的提醒會被調成背景噪音（`_core`：強調是預算）。

## 被否決的選項
- **`next` 直接建議 TDD**：進口意見，見上 1。
- **`next` 建議去裝 SpecKit**：推銷第三方工具＝站進平台位置，正是 README 那張「knowie 在 spec 工具**底下**」的圖拒絕的姿勢。偵測到就交接，這本來就有。
- **git 提醒也放 `next` 或 judge 每輪報**：這次只做 `init` 的一次性檢查。judge 把它當降級項回報是可加的後續，但別兩處都念。
