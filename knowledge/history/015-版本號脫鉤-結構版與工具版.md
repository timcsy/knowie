# 015：版本號脫鉤 — 結構版與工具版分開，breaking 可以有、靜默不行

> 2026-06-07。一條相容性策略的決策轉移。由「結構改過（research/design/history → concepts/episodes/history/draft）之後，十幾個既有專案全是舊的」這個真實處境驅動。

## 轉移
- **舊（superseded）**：`.knowie.json` 只有一個 `version`，而 `init`/`update`（CLI）**無條件**寫 `config.version = VERSION`。結果是舊結構專案跑一次 update 就被標成新版——結構沒遷、版號卻說遷了，這是**靜默 breaking**。設計上當時還寫著「向後相容是硬約束」。
- **新（current）**：`structureVersion`（`src/constants.js` 的 `STRUCTURE_VERSION`）與 tool `version` **脫鉤**，只在結構真的改時才升。CLI 只升 tool version、**不碰** structureVersion；落後就印 `structureBehind` 警告；structureVersion 只在 `/knowie-migrate` 實際遷移之後才升。**不做向後相容，但不靜默 breaking。**

## 為什麼變
1. **向後相容的價值 ∝ 使用者數 × 舊資料量**——當時兩者都 ≈ 0，成本卻 > 0。趁年輕做乾淨的 breaking change 是黃金窗口；向後相容是「老協議」（POSIX／FUSE）的約束，knowie 還沒到那個階段。
2. **breaking 不可怕，靜默 breaking 才可怕。** 所以砍掉相容性、但保留偵測。
3. **偵測不能只信版號**：改成比對當前正典訊號（`_core` 的 Structure 段 + `.templates/`），未來結構小改自動涵蓋，不必回頭改 skill。
4. **一個版號承載兩件事必然衝突**：工具每次發版都要升，結構幾個月才動一次。綁在一起就只能二選一——不是小改誤觸發遷移，就是真的結構改被吃掉。

## 修訂了什麼認知
「向後相容是硬約束」是從外部生態（語言、OS）借來的理論，被作者的真實處境（單人使用、多數專案根本還沒累積出子目錄）校正掉。
